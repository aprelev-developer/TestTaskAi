### T10 · граница · `?page=0`, `?page=-1`, `?page=abc`

- **Ожидалось:** детерминированный ответ, **одинаковая логика для всех трёх**, не 5xx
- **Факт:** логика разная:

  | Вход | Ответ | Сообщение |
  |---|---|---|
  | `page=0` | **400** | Page must be greater than 0 |
  | `page=-1` | **400** | Page must be greater than 0 |
  | `page=abc` | **200** | молча показана страница 1 |
  | `page=1.5` | **200** | молча показана страница 1 |
  | `page=` (пусто) | **200** | молча показана страница 1 |
  | `page=%20` (пробел) | **200** | молча показана страница 1 |
  | `page=99999999999999999999` | **200** | молча показана **страница 1** |

- **Вердикт:** ❌ **упала** → BUG-001
- **Отдельно опасное:** двадцатизначный номер страницы отдаёт не пустую выборку
  и не 400, а первую страницу — то есть значение, переполняющее int, молча
  превращается в «страницу по умолчанию»

### T11 · граница · `?sort=hacked`

- **Ожидалось:** откат к умолчанию либо 400, не 5xx, значение не в SQL
- **Факт:** **400**, «Invalid sort parameter. Allowed: date, views, title».

- **Примечание:** решение строгое (400), тогда как для `page` выбрано мягкое

# Исправления по итогам независимого аудита · 2026-08-17

## Изменённые вердикты

### T05 · было «✅ прошла» → **❌ упала** → BUG-004

Ожидание T05 гласило: «Заголовок, текст и **категории** поста отображены»
(множественное число), `SPEC.md` §5 сценарий 3 — «принадлежность к
категориям». Факт: пост 4 состоит в двух категориях (`design`, `programming`),
а его страница объявляет одну.

Я зачёл проверку пройденной, прочитав собственное ожидание в единственном
числе. Проверка должна была упасть. Оформлено как **BUG-004**, покрыто
автотестом (проверка T05c).

### T12 · часть «экранирование» · было «✅» → **не выполнена**

Вердикт был выставлен по входу `/category/<script>alert(1)</script>` → 404.
Этот вход отбрасывается маршрутизатором и до вывода не доходит вовсе, поэтому
ничего об экранировании данных не доказывает. Ожидание же было сформулировано
про данные: «HTML-спецсимволы **в данных** экранированы». Проверка снята с
вердикта и помечена как невыполненная.

### T12 · часть «1440» · фактически **1568 px**

Скриншоты сняты шириной 1568 px, а не 1440. То есть проверена одна ширина, и та
не та, что записана в плане. Файлы переименованы в `…-1568.jpg`.
Требование курса «две ширины, 360 и 1440» не выполнено **ни по одной**.

### T02 · доказательство заменено

К T02 (`/category/programming`) был приложен скриншот категории `technology`.
Ожидание «заголовок соответствует слагу» этим снимком не проверяется. Вердикт
T02 держится на логах; снимок оставлен как иллюстрация страницы категории.

### T03 · числа в «Факте» не подтверждаются артефактами

Приведённый порядок `[4, 24, 22, 20, 16, 1, 12, 10]` не совпадает ни с
`probe-edge.log` (`[4, 22, 1, 24, 20, 16, 12, 10]`), ни с `probe-http.log`, и
вдобавок не является убывающим по просмотрам ни при одном зафиксированном
наборе. Вердикт «прошла» верен — живая проверка сортировку подтверждает, — но
конкретные числа были восстановлены по памяти, а не выписаны из лога. Опираться
на них нельзя.

## Снятая находка

### Дата постов — **дефекта нет**, «подтверждение» было ошибочным

В `qa/discrepancies.md` (D-2) и `naive-run/COMPARISON.md` я объявил
подтверждённой находку наивного прогона «шаблон печатает сегодняшнюю дату
вместо `published_at`». Проверка по объекту и базе:

```
grep -rn "published" database/ app/ resources/   → пусто, колонки нет
migration: created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
seeder:    INSERT INTO posts (title, slug, description, content, image)  ← created_at не задан
SELECT id, created_at FROM posts → все 25 постов: 2026-08-17 13:16:50
```

Дата на карточках **верна** — это настоящий `created_at`. Все посты созданы в
одну секунду сидером, поэтому даты и совпадают. Наивный прогон ошибся, а моя
«перепроверка» проверяла следствие, одинаково согласующееся и с гипотезой, и с
её отрицанием.

**Следствие для T02 и T03:** `?sort=date` работает на сплошных ничьих, поэтому
порядок `[24,22,20,16,12,10,4,1]`, использованный как эталон, — произвольное
разрешение ничьей, а не результат сортировки по дате. Контракт «сортировка по
дате» на сидовых данных непроверяем в принципе.
