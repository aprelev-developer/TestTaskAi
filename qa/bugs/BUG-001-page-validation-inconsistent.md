# BUG-001 · Параметр `page` валидируется несогласованно: `0` и `-1` дают 400, а `abc`, пустое значение и 20-значное число молча открывают первую страницу

- **Серьёзность:** значительная
- **Компонент:** `GET /category/{slug}`, query-параметр `page`
- **Проверка тест-плана:** T10
- **Окружение:** http://localhost:8080, Docker, сид 6 категорий / 25 постов

## Шаги воспроизведения

1. Открыть `http://localhost:8080/category/programming?page=0` → 400,
   «Page must be greater than 0»
2. Открыть `http://localhost:8080/category/programming?page=-1` → 400, то же сообщение
3. Открыть `http://localhost:8080/category/programming?page=abc` → **200**,
   показана первая страница, никакого сообщения об ошибке
4. Открыть `http://localhost:8080/category/programming?page=` (пустое значение)
   → **200**, первая страница
5. Открыть `http://localhost:8080/category/programming?page=1.5` → **200**, первая страница
6. Открыть `http://localhost:8080/category/programming?page=99999999999999999999`
   → **200**, показана **первая** страница

## Ожидаемый результат

Единая логика обработки некорректного значения `page`: либо все некорректные
значения отклоняются с 400, либо все нормализуются к странице 1. Источник:
`SPEC.md` §9, T10 — «Детерминированный ответ… **одинаковая логика для всех
трёх**». `README.md` объекта задаёт только `page — пагинация (по умолчанию: 1)`
и способа обработки мусора не описывает, поэтому оценивается согласованность,
а не конкретный код ответа (`SPEC.md` §10, U3).

Отдельно по шагу 6: число, превышающее диапазон целого, — это запрос страницы,
которой заведомо нет. Ответ «вот первая страница» неверен при любой из двух
допустимых стратегий.

## Фактический результат

Приложение делит некорректные значения на две группы с противоположным
поведением:

| Вход | Код | Что показано |
|---|---|---|
| `page=0` | 400 | Page must be greater than 0 |
| `page=-1` | 400 | Page must be greater than 0 |
| `page=abc` | 200 | первая страница, молча |
| `page=1.5` | 200 | первая страница, молча |
| `page=` | 200 | первая страница, молча |
| `page=%20` | 200 | первая страница, молча |
| `page=99999999999999999999` | 200 | **первая** страница, молча |

Тот же приём с параметром `sort` даёт третью логику: `?sort=` (пустое значение)
возвращает **400**, а `?page=` (пустое значение) — **200**. То есть два
соседних параметра одной страницы обрабатывают пустую строку противоположным
образом.

## Доказательство

`qa/evidence/probe-edge.log` — вывод `qa/evidence/probe-edge.py`, все семь
входов подряд с кодами ответа и текстом страницы.

**Чем пойман:** разбором кодов ответа, а не скриншотом. Скриншотом этот дефект
не доказывается: суть в **несогласованности между входами**, а один снимок
показывает один вход и выглядит совершенно нормально.

## Почему это дефект

Читатель, у которого номер страницы съехал (битая ссылка, ручная правка URL,
рассылка с поломанным параметром), получает разный результат от почти
одинакового мусора: где-то честную ошибку, где-то молчаливую подмену на первую
страницу. Молчаливая подмена хуже: человек считает, что видит страницу 3, а
видит страницу 1, и не узнает об этом. Для поисковых роботов это ещё и
бесконечный набор URL с одинаковым содержимым.
