# BUG-003 · Приложение отвечает 405 на HEAD-запрос к любой странице, включая главную

- **Серьёзность:** значительная
- **Компонент:** роутер, обработка HTTP-методов
- **Проверка тест-плана:** вне плана, найдено попутно при проверке методов
- **Окружение:** http://localhost:8080, Docker, сид 6 категорий / 25 постов

## Шаги воспроизведения

1. Выполнить `curl -I http://localhost:8080/`
2. Посмотреть код ответа и заголовки
3. Повторить для `curl -I http://localhost:8080/post/4` и
   `curl -I http://localhost:8080/category/programming`
4. Для сравнения выполнить `curl -D - -o /dev/null http://localhost:8080/`

## Ожидаемый результат

`HTTP/1.1 200 OK` с теми же заголовками, что у GET, и пустым телом.

Источник — RFC 9110 §9.3.2: сервер, поддерживающий GET для ресурса, обязан
поддерживать и HEAD, а ответ на HEAD должен совпадать с ответом на GET за
вычетом тела. Это не трактовка неописанного случая: HEAD не относится к
неоднозначностям `SPEC.md` §10, потому что поведение задано стандартом,
а не README объекта.

## Фактический результат

```
$ curl -sS -I http://localhost:8080/
HTTP/1.1 405 Method Not Allowed
Server: nginx/1.29.6
Date: Mon, 17 Aug 2026 13:38:46 GMT
Content-Type: text/html; charset=UTF-8
Connection: keep-alive
X-Powered-By: PHP/8.3.33
```

То же самое для `/post/4` и `/category/programming`. GET на те же адреса
возвращает 200.

Ответ формирует **само приложение**, а не веб-сервер: в ответе присутствует
`X-Powered-By: PHP/8.3.33`, тогда как отброшенные nginx методы (PUT, DELETE)
дают ответ с телом `405 Not Allowed nginx/1.29.6` и без этого заголовка.
То есть запрос дошёл до PHP, роутер не нашёл маршрута для метода HEAD и выбросил
`MethodNotAllowedException`.

## Доказательство

`qa/evidence/probe-edge.log`, раздел «--- методы ---», и приведённый выше вывод
`curl -I` с заголовком `X-Powered-By`, который и указывает на слой приложения.

**Чем пойман:** разбором ответа. Скриншотом этот дефект не ловится в принципе —
браузер при обычном просмотре HEAD-запрос не делает, на экране всё выглядит
исправно, и визуальная проверка прошла бы мимо.

## Почему это дефект

HEAD используют мониторинг доступности, чекеры ссылок, прокси и поисковые
роботы — как дешёвую замену GET, когда тело не нужно. Для всех них сайт
выглядит нерабочим: аптайм-монитор покажет падение, чекер пометит все ссылки
битыми, робот может понизить страницы в выдаче. При этом реальные читатели
проблемы не увидят, поэтому дефект способен прожить в продакшене долго.
